# 動物パズル ルール拡張と難易度基準 設計書

作成日: 2026-09-03

## 1. 背景

出荷済み18ステージが「簡単すぎる」という問題に対し、全ステージを計測した。

| stage | 幾何解 | 必要な思考レベル | ルール手数R |
|---|---|---|---|
| 1, 2, 5 | 1 | L0（詰め方が1通りしかない） | 0 |
| 3, 4, 6, 10, 11, 12, 17 | 2〜3 | L1 | 0〜1 |
| 7, 8, 9, 13, 14, 15, 16, 18 | 6〜20 | L1 | 2〜3 |

判明した原因は3つ。

1. **stage-1/2/5 は幾何的な詰め方が1通りしかない**。ルールが一切仕事をしておらず、ただの型はめ。
2. **最難関でもルールを使う手は3手だけ**。残りはジグソーパズルで、盤面を広げても手数が増えるだけで思考量は増えない。
3. **ルールの語彙がほぼ空**。7種のうち条件を持つのはシマウマとキリンの2種だけで、リス・ライオン・ゾウは条件ゼロ。実装済みの `minDistance` / `flockRequired` / `symbiosisRequired` と、ワニ・ウシツツキは一度も使われていない。

本設計は、この3つを「ルールの語彙拡張」と「機械的に検証できる難易度基準」で解決する。

## 2. 目的とゴール

- ステージの良し悪しを**数値で判定できる**ようにし、自動テストで守る。以後の指示は「★4を3面追加して」で通るようにする。
- 難易度を**章の進行だけに比例**させる。駒数は章と無関係にする。
- ゲームの主眼を「形を詰める」から「**ルールから配置を論理的に推理する**」へ移す。

### 非ゴール

- 形（ポリオミノ）の廃止。**形は維持する。**
- 空きマスの許容。**ぴったり埋め切る仕様を維持する。**
- 盤面5×5固定。**5〜8の可変を維持する。**
- 唯一解の緩和。**唯一解を必須のまま維持する。**

## 3. スコープ

参照仕様書（条件付きマス配置パズル仕様書）から**採用する**もの:

- 条件語彙の拡張（ななめ隣接禁止／まわり8マス／上下左右／同じ行・列とその禁止／ちょうど○マスはなす）
- 条件の達成状況を ✓ / ❌ でリアルタイム表示
- 難易度を「条件の数」でも段階付けする考え方（EASY 2〜3 … HARD 5〜8）

**採用しない**もの:

- 1マス1キャラ（形なし）
- 空きマス許容
- 5×5固定
- 唯一解を必須としない方針
- 特殊マス（乗れるマスに属性を持たせる方式）
- キャラ個体ごとの条件定義
- 一直線・挟む・複数キャラ条件（将来の拡張候補として保留）

## 4. 盤面モデル：地形からブロックへ

「乗れるマスの属性で置ける動物を限定する」方式（water地形にはワニしか置けない等）は**廃止する**。候補が機械的に絞られてかえって簡単になり、地形ごとに専用動物が必要になって種類が膨張するため。

代わりに、盤面は「**置けるマス**」と「**置けないブロック**」の2種類だけにする。ブロックには種類があり、**条件から参照される**（例：ワニは水ブロックのとなりが必要）。

```ts
export type BlockKind = 'wall' | 'water' | 'tree';
export type CellTerrain = 'land' | BlockKind | 'void';

/** 条件から参照できるブロック。草むら(wall)は仕切り専用なので含めない。 */
export type ConditionBlock = Exclude<BlockKind, 'wall'>;
```

- `land` … 動物を置けるマス（唯一の配置可能マス）
- `wall` … 草むら。既存の壁と同じ、条件から参照されない純粋な仕切り
- `water` … 水ブロック（新規）。**意味が変わる**：従来は「ワニが乗れるマス」だったが、今後は「誰も乗れないブロック」
- `tree` … 木ブロック（新規）
- `void` … 盤外

`AnimalDef.terrain` と `Terrain` 型（land/water/sky）は**削除する**。`sky` は消滅する。

見取り図の文字割り当て: `.`=land, `#`=wall, `~`=water, `T`=tree, `x`=void

`validateStage` の「地形ごとにマス数一致」検証は「**land の総数 ＝ 全動物の占有マス数の合計**」だけに簡約される。

## 5. 条件モデル：2層構造

現在の条件は `SPECIES` テーブルに種ごとに書かれ、全ステージで共通に適用される。しかし「AはBより上」「AとBは同じ列」のような位置関係は動物の性格ではなく、そのステージの出題である。「キリンは常にライオンより上にいる」を全ステージに課すのは成立しない。

そこで条件を2層に分ける。

### 5.1 種の性格（`SPECIES`、全ステージ共通）

動物図鑑として一貫する、その動物が持つ性質。

```ts
export type SpeciesCondition =
  | { kind: 'adjacentForbidden'; with: Species }
  | { kind: 'adjacentRequired'; with: Species }
  | { kind: 'flockRequired' }
  | { kind: 'diagonalForbidden'; with: Species }
  | { kind: 'surroundForbidden'; with: Species }
  | { kind: 'minDistance'; from: Species; distance: number }
  | { kind: 'blockAdjacentRequired'; block: ConditionBlock }
  | { kind: 'blockAdjacentForbidden'; block: ConditionBlock };
```

既存の `symbiosisRequired` は `adjacentRequired` に改名する（意味は同一）。

### 5.2 ステージ限定ルール（`Stage.rules`、そのステージのみ）

出題側の仕掛け。ステージデータに書く。

```ts
export type StageRule =
  | { kind: 'above'; a: Species; b: Species }
  | { kind: 'leftOf'; a: Species; b: Species }
  | { kind: 'sameRow'; a: Species; b: Species }
  | { kind: 'sameCol'; a: Species; b: Species }
  | { kind: 'differentRow'; a: Species; b: Species }
  | { kind: 'differentCol'; a: Species; b: Species }
  | { kind: 'exactDistance'; a: Species; b: Species; distance: number };

export type Stage = {
  /* ...既存フィールド... */
  rules?: StageRule[];
};
```

「下」「右」は `above` / `leftOf` の引数を入れ替えたものと同値なので、条件種別としては追加しない（表示文言の側で「BはAより下」と読み替える）。

**同種が複数いる場合の意味**: ステージ限定ルールは、種Aの**全個体**と種Bの**全個体**の**全ペア**について成立することを要求する。

## 6. 条件の厳密な定義

駒は複数マスを占有するため、すべての条件を「**駒の占有マス集合**」で定義する。

| 条件 | 定義 |
|---|---|
| となりに置けない / となりが必要 | 2つの駒の占有マス間に、マンハッタン距離1の組が存在するか |
| 同じ仲間ととなり合わせる（群れ） | 同種の別個体と上記の意味で隣接 |
| ななめのとなりに置けない | 2つの駒の占有マス間に、行差1かつ列差1の組が存在しないこと |
| まわり8マスに置けない | 直交隣接・斜め隣接のいずれも存在しないこと |
| ○マス以上はなす | 2つの駒の占有マス間の**最小**マンハッタン距離 ≧ ○ |
| ちょうど○マスはなす | 上記の最小距離が厳密に ○ |
| 指定ブロックのとなりが必要 / 禁止 | 駒の占有マスのいずれかが、そのブロックのマスと直交隣接するか |
| AはBより上 | Aの占有マスの**最大行** < Bの占有マスの**最小行**（完全に上にある） |
| AはBより左 | 列について同様 |
| 同じ行にいる | Aの占有**行**集合と Bの占有行集合が交わる |
| 同じ列にいる | 列について同様 |
| 同じ行／列に置けない | 上記が交わらない |

## 7. 動物ロースター

ルール手数を上げる原理は「**形では見分けがつかず、ルールでしか置き場所が決まらない駒を並べる**」こと。1x1・縦2・2x2にそれぞれ3種を配置する。

| 形 | 動物 | 性格 | 状態 |
|---|---|---|---|
| 1x1 | リス | ライオン・ヒョウのとなりに置けない | 条件を新規付与 |
| 1x1 | サル | 仲間のとなりが必要（群れ）＋ ヒョウのとなり不可 | 新種 |
| 1x1 | ウシツツキ | キリンのとなりが必要 | 実装済み・初投入 |
| 縦2 | ライオン | 同種のとなりに置けない（縄張り） | 条件を新規付与 |
| 縦2 | キリン | ライオンのとなりに置けない | 据え置き（ワニ条件は削除） |
| 縦2 | ヒョウ | 同種のとなり不可 ＋ サル・リスのとなり不可 | 新種 |
| 横2 | シマウマ | ライオンのとなりに置けない | 据え置き |
| 横2 | ワニ | 水ブロックのとなりが必要 | 実装済み・初投入 |
| 2x2 | ゾウ | リス・サルのとなりに置けない（ふんでしまう） | 条件を新規付与 |
| 2x2 | サイ | 同種から3マス以上はなす | 新種 |
| 2x2 | ゴリラ | 木ブロックのとなりが必要 | 新種 |

「縄張り」は `adjacentForbidden` の `with` に自分自身の種を指定することで表現する（`neighborsOf` が自分自身の個体を除外するため、既存の判定ロジックがそのまま使える）。

ゾウを「群れ」にしない理由: `validateStage` が `flockRequired` を持つ種に2体以上を要求するため、ゾウ1体だけのステージが作れなくなる。盤面の自由度を優先した。

## 8. 難易度の基準

### 8.1 思考レベル L1〜L4

数独の難易度判定と同じく、強さの異なるソルバーを順にぶつけ、**そのステージを解くのに最低限必要な思考の段数**を難易度とする。

伝播（propagation）の定義: 以下を繰り返す。

- **naked single** … ある種の置ける場所が1つしかない → 確定
- **hidden single** … ある空きマスを覆える候補が1つしかない → 確定
- 候補は「地形・重なり」と「単調な条件（置くと即座に破れる条件）」で絞る

| レベル | 定義 |
|---|---|
| **L0** | 幾何的な詰め方が1通りしかない（ルールが仕事をしていない）**＝不合格** |
| **L1** | 伝播だけで最後まで解ける |
| **L2** | 伝播が詰まり、**深さ1の背理法**が必要（候補を1つ仮置きして伝播させ、矛盾すればその候補を消す） |
| **L3** | **深さ2**の背理法が必要 |
| **L4** | **深さ3以上**が必要 |

**矛盾の定義**: 伝播の結果、(a) まだ置いていない種の候補がゼロになる、(b) 空きマスのうち、どの候補にも覆われないマスができる、のいずれか。

**判定手順**: L1のソルバーで解ければ L1。解けなければ深さ1の背理法を許して再試行し、解ければ L2。以下同様に深さ2で L3、深さ3で L4。深さ3でも解けない場合は `unsolvable` を返す（この場合ステージは不合格）。ただし幾何解が1通りのステージは、レベル判定より先に **L0** として不合格にする。

### 8.2 ルール手数 R

解答トレース上で、**その手の直前の状態において、地形と重なりだけを見た候補が2つ以上あり、条件を適用して初めて1つに絞れた手**の数。

この定義を採る理由: 「正解のうち幾何的に位置が揺れる駒の数」で測ると stage-9/13/14 は R≒6 となり基準を満たしてしまうが、実際には最初の2手でルールを使えば後は形が勝手に決まる。トレース上で数えると同じステージは R=2〜3 になる。**Rを課すことは、ルールを使う場面が解答の最初から最後まで散らばっていることを要求する**ことを意味する。

トレースは決定的にする。各手では、**条件を適用した後の候補数が最小の種**を選び、同点なら種名の辞書順、それでも同点ならアンカーの行→列の順で選ぶ。Rを数えるときの「地形と重なりだけを見た候補」は、その時点で盤面に置かれている駒との重なりのみを考慮し、条件は一切適用しない。

### 8.3 条件数

そのステージで**実際に効いている**条件の数。種の性格とステージ限定ルールを合わせた各条件について、**その条件だけを外すと解が2つ以上になる**ものを数える。効いていない飾りの条件は数えない。

### 8.4 章ごとの合格ライン

**2026-09-04三度目の改訂（6章構成→3章構成）**: 当初は「1章・2〜4章・5〜6章」の6章30面前後を想定していたが、分割3のTask 4完了後の再々レビューで、鏡像パターン（左右・上下反転）による見かけ上の重複を正しく除外すると、L3以上の面は現行の地形12種・動物11種の語彙で実質3種類、L4の面は実質2種類しか作れないことが判明した。5〜6章分の面数を確保できないため、章数そのものを縮小した（ユーザー承認済み）。

| | 必要レベル | ルール手数R | 駒数 |
|---|---|---|---|
| 1章（導入） | L1〜L2 | 0〜3 | 制約なし |
| 2章 | **L3のみ**（L4は3章に確保するため上限を持つ） | 合否に使わない（参考値） | 制約なし |
| 3章（終盤） | **L4** | 合否に使わない（参考値） | 制約なし |

**駒数は章の進行と無関係にする。** 1章に駒8体の面があっても、3章に駒5体の面があってもよい。難易度指標だけが章に比例する。

**2026-09-04改訂**: 当初案（2〜4章R≧4、5〜6章R≧5）は分割2実装後のスパイク検証（6種の生成戦略、既存18ステージの実測を含む）で、**R≧4が事実上ほぼ到達不能**と判明したため引き下げた。

原因は構造的：Rは「幾何的には2択以上あるが、条件を適用して初めて1つに絞れた手」の数だが、
- 同条件の駒を増やすと駒同士が入れ替え可能になり**唯一解が壊れる**
- 唯一解を保ったまま駒を増やすと、対称な駒同士の解決は「仮置きして矛盾を確認する」（＝L2以上の背理法）になり、**Rには寄与しない**（背理法で確定した手はRの定義上カウントされない）

この2つの失敗モードの間に「R≧4」を満たす余地がほとんど無い。駒数上限8体・現行の条件語彙の下では、Rの実測上限は2〜3（スパイクでの最大値2、既存18ステージの最大値3＝stage-13）。**レベル（L1〜L4）は当初案のまま維持する**——L4への到達率はスパイクで300〜450試行あたり6〜17件（2〜4%）と、生成器が十分な試行数を回せば現実的な範囲だったため。

**2026-09-04再改訂（条件数の欄を削除）**: 分割3の生成器実装中のスパイク検証で、**「効いている条件数」は章をまたいで一切差が出ない**ことが判明したため、章の合格ラインから外した（`gradeStage`の参考値としては残す）。

原因は`countEffectiveConditions`の数え方にある。「その条件を1つ外すと解が増えるか」を**種・条件の定義単位**で数えるため、同じ条件（例：複数のキリンが共有する「ライオンのとなり不可」）を何体の個体が担っていても1としか数えない。加えて、ぴったり敷き詰めるステージは構造的に「駒を動かせる自由度」がほぼ1箇所しかない（幾何的に入れ替え可能な区画は複数あっても、大抵は同じ条件がそれら全部を一括で解決してしまう）。この2つが重なり、幾何解2通り以上・唯一解という他の絶対条件を満たすステージは、地形テンプレート12種・唯一解サンプル227件超で**例外なく**`effectiveConditions === 1`になった。手作りの独立した2領域（別々の条件で別々に確定する構成）でも試したが、章をまたいで意味のある差を作れる見込みが立たなかった。

**2026-09-04三度目の改訂（ルール手数Rを全章共通の最低ラインに統一）**: 分割3のTask 4実行時、実際に組み上がった生成器（`compose-animals.ts` + `PATTERNS`、ステージ限定ルールは使わない）で章ごとの合格ラインを満たす面を集めようとしたところ、**2〜4章の`R≧2`が唯一解サンプル1,158件超で一度も出現しなかった**（5〜6章の`R≧3`は検証するまでもなく同様）。原因はeffectiveConditionsの件と同根：この生成器が使う非対称な種（リス・シマウマ・キリン）のほとんどが`adjacentForbidden(lion)`という同一の条件を共有しており、複数体が同時に居ても「ルールで初めて1つに絞れた」独立した手として複数積み上がらない。ステージ限定ルール（`Stage.rules`）を使えばR≧2は稀に出現する（唯一解サンプルの約0.5%）ことも確認したが、R≧3は依然として0件、かつ生成器に組み込むには追加の実装コストがかかる。

対応として、Rの下限を**全章共通で1以上**（純粋な幾何だけでは解けないことの確認）に統一し、章をまたぐ難易度の差別化は**思考レベル（L1〜L4、必要な背理法の深さ）1本に一本化した**。この軸はスパイク・実装の両方で一貫して信頼できることが検証されている（L4への到達率は300〜450試行あたり6〜17件、2〜4%）。ステージ限定ルールを生成器に組み込んでRをさらに底上げする改善は、将来の拡張候補として14節に記載する。

### 8.5 全ステージ共通の絶対条件

1. 解がちょうど1通り
2. 幾何的な詰め方が2通り以上（＝L0でない）
3. 全マスがブロックの行・列がない（既存 `findDesignWarnings` の `deadEdgeRow` / `deadEdgeCol`）
4. 孤立した1マスの `land` がない（既存 `isolatedSingleCell`）
5. 2章以降は、**同じ形の駒が2種以上登場する**こと（幾何的に見分けのつかない駒がなければ R は上がらない）

### 8.6 API

```ts
export type SolverLevel = 'L0' | 'L1' | 'L2' | 'L3' | 'L4' | 'unsolvable';

export type StageGrade = {
  solutions: number;          // 1 でなければ不合格
  geometricPackings: number;
  level: SolverLevel;
  ruleMoves: number;          // R
  effectiveConditions: number; // 参考値。章の合否には使わない(8.4節2026-09-04再改訂を参照)
  warnings: DesignWarning[];
};

export const gradeStage = (stage: Stage): StageGrade;
export const meetsChapterBar = (grade: StageGrade, chapterNumber: number, stage: Stage): string[]; // 違反理由の配列
```

## 9. ステージ生成器

L3以上のステージを25面以上手で描くのは現実的でない（現行18面が偶然すべてL1〜L2に収まっているのは、手で盤面を描くとこの範囲に落ちるため）。生成して選別する。

開発時に実行するスクリプトとして実装する（アプリには同梱しない）。

1. 盤面サイズ（5〜8 × 5〜8）とブロック配置をランダム生成
2. `land` のマス数に合う動物構成を選ぶ
3. `validateStage` を通す
4. `countSolutions` が1であることを確認
5. `gradeStage` を実行し、目標の章の合格ラインを満たすものだけ採用
6. 章ごとに必要数が集まるまで繰り返す
7. `stages.ts` に貼り付けられる形式で出力

**2026-09-04追記（スパイク結果）**: §8.4に記載のとおり、当初の R≧4/R≧5 目標は6種の生成戦略による実地検証の結果、実測上限（R≦2〜3）を超えており事実上到達不能と判明したため、目標値そのものを引き下げた（現行値: 2〜4章R≧2、5〜6章R≧3）。この引き下げにより、単純なランダム生成＋フィルタでも目標達成が現実的になっている。レベル（L1〜L4）は引き下げ不要だった——スパイクでL4への到達率は300〜450試行あたり6〜17件（2〜4%）だった。

**構成のコツ（スパイクで判明）**: 同一条件を持つ駒を増やしすぎると駒同士が入れ替え可能になり唯一解が壊れる。対称な自己回避条件（縄張り等）を持つ駒を複数体並べるとL2以上の背理法が必要になりレベルは上がるが、背理法で確定した手はRにカウントされないためRは伸びない。Rを稼ぐには、非対称な「特定の相手を避ける／必要とする」条件を持つ駒を、それぞれが幾何的には複数候補を持つ配置で使うのが効く。

**既知の制約（章をまたぐステージ内容の重複、および2〜4章のL4上限）**: `generateForChapter`の重複除去（`seen`集合）は本来、同じ合格ラインを共有する章（2〜4章はL3、5〜6章はL4）どうしで共有すべきだが、これを怠ると章をまたいで同一の(地形×種構成)ステージが繰り返し採用されうる（分割3のTask 4完了直後のレビューで、3章が2章の完全な重複になっていたことが発覚し、生成ランナーで`sharedSeen`を導入して修正した）。加えて、2〜4章の合格ラインに元々レベルの上限（L4を含む「L3以上」）が無かったため、希少なL4面が2〜4章の探索に消費されてしまい5〜6章向けのプールが枯渇する問題も見つかり、2〜4章に`maxLevel:'L3'`の上限を追加して解消した。地形パターンも8スロットの大規模パターンを左右・上下反転で12種に増やし、組み合わせの枯渇そのものを緩和した（`scripts/stage-patterns.ts`）。それでも12パターン・現行の種の組み合わせで到達できるL3・L4ステージの絶対数には限りがあり、章ごとの必要面数を機械的に5に固定すると生成に失敗する場合がある（`scripts/generate-stages.ts`の`CHAPTER_DEFS`で章ごとに`needed`を個別調整する運用としている）。
